# SPEC-029: Invoke API — Synchronous Graph Invocation, Contract, and Per-Graph API Keys

**Status:** Implemented — verified live, full test suite passing
**Milestone:** Deployable-workflow platform push
**Author:** Rohan
**Depends on:** SPEC-010 (run persistence — `RunResult`/`TraceRecord` shape, `runs_store`), SPEC-015 (graph persistence — `graphs_store`, `GraphRow`), SPEC-017 (production hardening — the existing shared `AGENT_GRAPH_STUDIO_API_KEY` credential and `require_auth`), SPEC-020 (platform authentication — JWT sessions, `AuthenticatedUser`), SPEC-021 (per-user app connections — `resolve_connections`/`resolve_connection_profiles`, shared-graph slot mapping)

## 1. Goal

Give an external caller a stable way to run one specific saved graph as a callable operation — `POST` a JSON object of named inputs, get a JSON object of named outputs back, synchronously, authenticated by a credential scoped to that one graph. This is the missing piece identified in this project's own strategic roadmap review as the core blocker to using a graph as the backend of a real product: today a caller either has to submit the entire graph JSON body on every call (`POST /runs`), or use the fire-and-forget webhook trigger and separately poll `GET /runs/{run_id}` for a result.

## 2. Why this, why now

`POST /runs` requires the caller to already possess and resubmit the full internal `GraphSpec` (every node, every edge, every config value) on every invocation — it is a "run this graph definition" endpoint, not a "call this saved workflow" endpoint, and it authenticates with the same all-graphs shared API key or a human JWT, never a credential scoped to one graph. The webhook trigger path (SPEC-009/012) is fire-and-forget by design (a `run_id` comes back immediately, the actual result has to be polled separately via `GET /runs/{run_id}`) — correct for its purpose (external event sources like Telegram), wrong for a synchronous "call this function, get the answer" integration pattern, which is what turns a graph into something embeddable in another application's request/response cycle.

Without this, "build a workflow, then call it from another app" requires the caller to reverse-engineer both problems above per integration. This spec closes that gap using only mechanisms already proven elsewhere in this codebase — no new execution model, no new node types.

## 3. Scope

**In scope:**

- **`POST /graphs/{graph_id}/invoke`** — takes `{"inputs": {...}}`, loads the persisted graph (never accepts a graph body), runs it synchronously (blocking the HTTP request, reusing `run_graph()` directly — no `BackgroundTasks` dispatch), returns `{"outputs": {...}}` on success.
- **An explicit graph contract, derived from existing graph structure, not new metadata.** A graph's external inputs are its `text_input` nodes; its external outputs are its `text_output` nodes. This reuses the exact mechanism `RunResult.result` already implements (`backend/execution/engine.py:207-208` populates `result[node_id]` for any node type with a `result_slot`, which `text_output` already declares) — no new schema layer for outputs. For inputs, invoking with a named value writes into that `text_input` node's `config.value` before the run (the same field `TextInputConfig` already defines), overriding whatever default was saved on the canvas.
- **A new optional `label` field on `TextInputConfig`/`TextOutputConfig`** (default `None`), settable from the node's config panel. When set, it is used as the external field name in `inputs`/`outputs` instead of the raw node id (e.g. `text_input_2`). This is the one genuinely new piece of schema in this spec — see §4 for why it's needed and why it's scoped this narrowly.
- **`GET /graphs/{graph_id}/contract`** — returns the derived input/output field list (name, source node id, whether a default value exists) so a caller can discover what to send without reading the graph JSON.
- **Per-graph invoke keys**: `POST /graphs/{graph_id}/invoke-keys` generates a new key, shown once in plaintext at creation (never retrievable again, matching every real API-key platform's own convention), stored as a salted hash (`hashlib.sha256`, no existing hashing utility in this codebase to reuse — see §6). `GET /graphs/{graph_id}/invoke-keys` lists metadata only (label, created_at, last_used_at, prefix — never the secret). `DELETE /graphs/{graph_id}/invoke-keys/{key_id}` revokes one. Multiple named keys per graph (so one integration can be revoked without breaking another calling the same graph).
- **Invoke-key auth is scoped to exactly one route shape**: `Authorization: Bearer <invoke-key>` is accepted only by `POST /graphs/{graph_id}/invoke` and `GET /graphs/{graph_id}/contract`, checked against that specific `graph_id`'s keys — it must not authenticate any other route (not `/runs`, not `/connections`, not another graph's invoke endpoint). This is a new, narrower auth path alongside `require_auth`, not a change to it.
- **A bounded synchronous timeout, configurable per invoke key at creation time** (`timeout_seconds`, sensible default 60s, capped at some reasonable maximum — e.g. 300s — to prevent an accidentally-unbounded key from holding an HTTP connection open indefinitely) — if `run_graph()` doesn't finish in time, the endpoint returns a `504` with the `run_id` so the caller can fall back to polling `GET /runs/{run_id}` for the eventual result. The run itself is not cancelled; the graph continues running to completion or failure, its final state persisted via the existing `runs_store` exactly as any other run.
- **Frontend**: a minimal "Invoke keys" section in the graph's settings surface — generate/copy-once/revoke, and a read-only view of the derived contract (so an author can confirm what a caller will see before sharing a key).

**Out of scope (deliberately, future specs — matches this project's own "build in response to a real need" discipline):**

- **Rate limiting / usage counters per key.** Flagged as the very next roadmap item after this one; not bundled in here to keep this spec's surface reviewable.
- **Async invoke with a callback URL** for long-running graphs. The bounded-timeout-then-fall-back-to-polling behavior above is the v1 answer; a proper webhook-callback mode is deferred until there's a real graph that needs it.
- **Any input/output type beyond `TEXT`.** `text_input`/`text_output` are the only nodes in this codebase that currently serve as literal graph boundaries; extending the contract to other typed slots is future work if a real use case needs it.
- **Editing an invoke key's scope/permissions.** A key can invoke its one graph or be revoked; nothing more granular for v1.
- **Multi-tenancy, graph versioning, embeddable widgets, sub-graph composition.** Unchanged from the roadmap review — later items, not this spec.

## 4. Design decisions (resolved)

- **Contract = existing `text_input`/`text_output` nodes, not a new "graph interface" schema.** Considered inventing a dedicated `GraphContract` model declared separately from the graph's nodes; rejected because this project already has exactly one designated "external boundary" node pair (`text_input` has no inputs, `text_output` has no outputs — `RunResult.result` already special-cases `text_output` for the same reason), and a second, parallel way to declare "this is an external input" would duplicate that concept rather than reuse it.
- **New `label` field on `TextInputConfig`/`TextOutputConfig`, not raw node ids as the API contract.** Node ids are auto-generated (`nextNodeId` in `Canvas.tsx` — `text_input_2`, `text_input_3`, ...) and not user-renamable from the canvas today; shipping an external API keyed by those ids would produce contracts like `{"text_input_2": "..."}` with no way for a graph author to fix it short of this spec also adding node-id renaming (a much larger, riskier change touching every edge reference). A single optional `label` string on exactly these two config models is the smallest schema addition that gives a real API-friendly contract, defaults to `None` (falls back to node id, so every existing graph invokes unchanged with zero migration), and follows the same per-node-type `config_model` pattern (`TextInputConfig`, `TextOutputConfig`) already established for every node type in this codebase.
- **Synchronous, not fire-and-forget, with a bounded timeout and a documented fallback.** `run_graph()` is already a plain blocking call safely callable from a sync route handler (Starlette dispatches sync `def` handlers to a worker thread automatically, same reasoning already documented at `submit_run`'s call site) — no new execution machinery needed. A hard timeout is required because some graphs (agent loops, long tool chains) can legitimately run for minutes, and holding an HTTP connection open indefinitely is not acceptable for a product-facing API; on timeout the caller gets the `run_id` and switches to the existing poll path rather than the request hanging.
- **Hashed-secret storage, not the existing Fernet-encrypted-connection-credential pattern.** `backend/connections/store.py`'s encryption (`ensure_encryption_key_configured`) is for credentials this app must later *retrieve and use* (outbound third-party API keys) — a fundamentally different threat model from an *inbound* bearer credential we only ever need to compare, never read back. Invoke keys follow the standard API-key pattern instead: generate a random token, show it once, store only `sha256(token)`; this is genuinely new infrastructure in this codebase (grepped — no existing hash-and-compare secret store to reuse) and is scoped to exactly this one new table.
- **A new, narrow auth path alongside `require_auth`, not a change to it.** `require_auth` (SPEC-017/020) is deliberately one dependency accepting either a human JWT or the single all-graphs shared key, applied globally to every route including dynamically-added ones. An invoke key must never work as a substitute for either of those (it must not list graphs, read connections, etc.), so it is checked inside the two new route handlers themselves, not folded into the global dependency — same reasoning already used in this codebase to keep the webhook routes' `?key=` trigger-secret separate from the global auth mechanism.

## 5. Data model / implementation notes

- New table `graph_invoke_keys` (new `backend/storage/invoke_keys_store.py`, mirroring the existing `graphs_store.py`/`runs_store.py` module shape): `key_id`, `graph_id`, `label`, `key_hash`, `key_prefix` (first ~8 chars of the plaintext, stored unhashed purely so a listing can show `agsk_7f3a...` for human identification, matching Stripe/GitHub's own convention), `timeout_seconds` (int, set at creation, default 60, capped at 300 — see §4/§7 resolution), `created_at`, `created_by`, `last_used_at`.
- `TextInputConfig`/`TextOutputConfig` (`backend/nodes/text_input.py`, `backend/nodes/text_output.py`) gain `label: str | None = None`.
- Routes and helpers live directly in `backend/api/app.py`, not a separate `invoke.py` — matches this codebase's actual, consistent convention (every route lives in this one module; a second file of route decorators would be a new, unprecedented split this app doesn't use anywhere).
  - `_build_contract(graph: GraphSpec) -> tuple[dict, dict, list[InvokeContractField], list[InvokeContractField]]` — walks `graph.nodes`, collects `text_input`/`text_output` nodes, computes each field's external name as `label or node.id`. Raises `ContractError` (→ 422) on a name collision within one direction.
  - **Correction to the original note above**: invoke overrides a `text_input`'s value by setting `node.config["value"]` directly, **not** `node.input_values`. `text_input` declares `inputs=[]` (see `backend/nodes/text_input.py`) — it has no input slots at all, so SPEC-025's `input_values` mechanism (which only satisfies a declared input slot with no incoming edge) has nothing to attach to; `execute_text_input` reads `config.value` directly, so that's the field invoke overrides. No `model_copy(deep=True)` is needed either — every call parses `GraphSpec.model_validate_json(graph_row.spec_json)` fresh from the stored string, and that parse is already an independent copy; mutating its `NodeSpec.config` dicts can never write back to `graphs_store`.
  - `POST /graphs/{graph_id}/invoke`: loads `GraphRow` via `graphs_store.get_graph`, 404s if missing; rejects unrecognized/missing-required input fields with 422; overrides supplied inputs (see correction above); calls `validate_graph`, `resolve_connections`/`resolve_connection_profiles` exactly as `submit_run` does (`user_id=graph_row.created_by`, no slot mappings — an invoke caller has no connections of its own to map); runs `runs.execute_run` on a `threading.Thread`, `.join(timeout_seconds)` (`DEFAULT_INVOKE_TIMEOUT_SECONDS = 60` for a JWT/shared-key caller, the invoke key's own `timeout_seconds` otherwise); `504` with the `run_id` if still running after the join (the daemon thread keeps running and persists its own final state via `execute_run`'s existing `finally` block — no separate persistence path needed); **discovered during implementation**: a single node's own execution error does *not* set `RunRecord.status = "failed"` — `backend/execution/engine.py`'s `_execute_node` catches it and records `error` on that node's own `TraceRecord` while the run otherwise completes normally (CLAUDE.md's "never silently swallow node execution errors" in action). An invoke caller needs a definitive pass/fail signal, so the route additionally scans `snapshot.trace` for any record with `error is not None` and returns `500` with `{"message", "failed_node_id", "run_id"}` if found — `snapshot.status == "failed"` alone is only reachable for a scheduler-level failure, which is rare. Returns outputs keyed by each `text_output`'s external name, reading from `RunResult.result.get(node_id)` (`.get`, not `[]` — a `text_output` skipped by a pruned conditional branch never gets a `result` entry, so its field comes back `null`, not a `KeyError`).
  - `GET /graphs/{graph_id}/contract`: same auth, returns `_build_contract`'s field list.
  - `POST|GET /graphs/{graph_id}/invoke-keys`, `DELETE /graphs/{graph_id}/invoke-keys/{key_id}`: standard auth only (`require_auth`'s tiers 1-2, JWT or the shared key) — deliberately excluded from the invoke-key-scoped route set, since key management is a human/admin action, not something an invoke key can do to itself.
  - Auth carve-out implementation: a third branch inside `require_auth` itself (`backend/api/app.py`), tried only when `request.scope["route"].path` is `/graphs/{graph_id}/invoke` or `/graphs/{graph_id}/contract` (`_INVOKE_KEY_SCOPED_ROUTES`) — not a second `Depends(...)`, since that would run *in addition to*, not *instead of*, the existing global dependency, and an invoke-key bearer would still 401 there first.
- Frontend: a new small panel section (likely inside `SettingsPanel` or a new tab on the graph's own settings, not the global app settings) — list keys, generate (shows the plaintext once in a copy-to-clipboard field with a "you won't see this again" notice, matching real API-key UX conventions; the creation form takes a `timeout_seconds` field, default 60), revoke; a read-only contract preview table (field name, direction, default, required/optional).
- `trigger_source="invoke"` is a new valid value alongside the existing `manual`/`webhook`/`schedule` (`runs.create_run`, `runs_store`). `HistoryPanel`'s `TRIGGER_FILTER_LABELS` map (added in the SPEC-028 redesign) gains an `"invoke": "Invoke"` entry alongside the existing three, so invoke-triggered runs are filterable in run history like any other trigger source — small, low-risk addition since the plumbing (`trigger_source` threaded through `create_run`/`execute_run`) already exists and only needs a new string value, not new machinery.

## 7. Open questions

- **Timeout value and configurability.** Resolved: configurable per invoke key at creation time (`timeout_seconds`, default 60, capped at 300) — not hardcoded, not per-graph. See §3/§5.
- **Should a `text_input`'s existing saved default make it optional for callers?** Resolved: yes — a non-empty saved `config.value` makes that field optional (the saved value is used if omitted); an empty saved value makes it required. No new "required" flag added. See §6.
- **Should `trigger_source="invoke"` be surfaced in `HistoryPanel`'s existing trigger-source filter as part of this spec?** Resolved: yes, included in this spec's scope. See §5/§6.
